You do not have to write `airship.yaml` or edit `runs-on` by hand. **Move
workflows** reads a repository's `.github/workflows`, suggests a runner for
each kind of machine your jobs use today, and shows the exact changes before
anything is written. Open it from **Repositories → Move workflows**, or from
the last step of **Set up**.

Nothing changes in the repository until you merge the pull request it opens.
Your choices are kept in the browser, so you can stop at any step and pick it
up later; every step can be skipped and revisited.

## What changes

- **`airship.yaml`** gains a definition for each new runner. If the
  repository already has one, the definitions are added to the end of its
  `runners:` list and the rest of the file is left as it is.
- **Each moved job's `runs-on`** becomes its runner's label with the run ID
  as a [suffix](/configuration/labels#always-add-the-run_id-suffix), and for
  a matrix job the leg's index too, so every leg gets a machine of its own:

  ```yaml
  runs-on: airship-linux--${{ github.run_id }}
  runs-on: airship-linux--${{ github.run_id }}-${{ strategy.job-index }}
  ```

  Only that value changes. Comments, quoting and everything else in the file
  stay exactly as they were.

A job can also use a label your `airship.yaml` or the organization's
[shared runners](/organization/runners) already serve.

## Windows and macOS jobs

They are not picked by default. A Windows job needs a runner with a Windows
image ([Windows runners](/configuration/windows)), and there are no macOS
images; the runner step warns about both before anything is written.

## Opening the pull request

The GitHub App opens the pull request only if it has Contents, Pull requests
and Workflows write access; GitHub refuses an app's changes under
`.github/workflows` without the last one. Without them the dashboard says
which to grant, and you can still download the files and commit them
yourself. See [the GitHub App's permissions](/self-hosting/github-app).
